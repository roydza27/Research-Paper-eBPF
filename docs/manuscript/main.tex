\begin{abstract}
Multi-tenant systems use extended Berkeley Packet Filter (eBPF) programs for networking, observability, and security in a shared kernel. Kernel-verifier acceptance does not guarantee compliance with a tenant-specific policy. This study examines a hybrid design combining conservative abstract analysis with symbolic-verification fallback. The analyzer returns SAFE, VIOLATION, or UNKNOWN; unresolved cases and analysis failures never authorize acceptance. The evaluation includes an audited baseline experiment (E1) and a controlled path-count experiment (E2). E1 suggests instruction count alone does not explain end-to-end verification time in the tested small corpus, while recorded E2 medians rise from 746.14 ms at one path to 1,231.16 ms at 64 paths. Raw E3--E5 artifacts were unavailable to the final independent audit, so reported hybrid discharge and savings figures remain unverified. The contribution is a conservative architecture, baseline characterization, and reproducible evaluation plan—not a confirmed general performance improvement.
\end{abstract}

\noindent\textbf{Keywords:} eBPF, multi-tenant cloud security, eBPF isolation, symbolic execution, abstract analysis, policy verification, KRAKENGUARD


\section{Introduction}

Cloud infrastructure increasingly consolidates multiple workloads on shared Linux hosts. This multi-tenant model improves utilization, but it also means that security mechanisms operating inside the kernel must distinguish what one tenant is authorized to do from what another tenant is allowed to do. Extended Berkeley Packet Filter (eBPF) provides a programmable interface for networking, tracing, observability, and security, making it attractive for cloud-native infrastructure. At the same time, its kernel-level execution model makes isolation and policy enforcement important security concerns.

The Linux eBPF verifier provides a fundamental safety gate, but verifier safety and fine-grained tenant policy compliance are different questions. A program may satisfy verifier safety requirements while still violating a tenant-specific policy governing helper calls, maps, memory, return values, or interactions with other programs. Recent systems have therefore explored fine-grained policy analysis and related verifier-assurance mechanisms, while broader studies characterize the Linux eBPF runtime and its operational context \citep{gbadamosi2024ebpfruntime}. KRAKENGUARD, for example, uses symbolic analysis to reason about fine-grained eBPF isolation policies and identifies symbolic path and expression growth as an important scalability concern \citep{patel2026krakenguard}. Other recent work addresses verifier precision through proof-guided refinement, verifier-resilient execution, verifier testing, tenant virtualization, and resource isolation \citep{sun2025bcf,sun2025aee,lyu2025veritas,zhang2026vbpf,carin2026peer}.

This work focuses on a narrower question within that broader multi-tenant security problem: whether expensive symbolic policy verification can be invoked selectively rather than universally. The central research question is:

\begin{quote}
Can fine-grained eBPF isolation policies be checked with predictable cost by combining inexpensive abstract analysis with selective symbolic execution?
\end{quote}

The proposed approach places a lightweight abstract policy analyzer before symbolic verification. The analyzer uses a conservative three-valued decision model: \textsc{Safe}, \textsc{Violation}, or \textsc{Unknown}. A proven safe program is accepted, a proven violation is rejected, and an unresolved program is forwarded to the frozen symbolic verifier. The design is intentionally fail-closed: lack of proof is not treated as safety.

The work does not replace the Linux verifier or KRAKENGUARD. It investigates a selective policy-analysis workflow and documents both its prototype design and the evidence required to evaluate its performance credibly.

The paper makes four contributions:
\begin{enumerate}
    \item We characterize the cost behavior of a frozen KRAKENGUARD configuration using controlled program-feature and symbolic-path experiments.
    \item We design a conservative abstract policy-analysis stage with explicit \textsc{Safe}, \textsc{Violation}, and \textsc{Unknown} outcomes.
    \item We implement a conservative three-valued abstract analyzer and specify how it integrates with symbolic fallback.
    \item We audit the strength and limits of the available evidence, separating measured baseline observations from Phase 5 results that are not independently reproducible from the audited repository state.
\end{enumerate}

\subsection{Background and Motivation}

\subsection{eBPF in Multi-Tenant Infrastructure}

eBPF allows user-supplied programs to execute at selected kernel hooks. In cloud infrastructure, XDP is one relevant hook because it enables high-performance packet processing close to the network receive path. The same programmability that makes eBPF useful also creates an isolation requirement: a tenant-specific program must remain within the authority defined for that tenant.

The security problem can be expressed as a policy decision over an eBPF program $P$ and policy $\Pi$:
\[
    V(P,\Pi) \in \{\mathrm{COMPLIANT},\mathrm{VIOLATION}\}.
\]
The policy may constrain operations such as helper calls, map accesses, memory behavior, or return values. The important distinction is that policy compliance is workload- and tenant-specific, whereas verifier safety is a more general property of whether the program is safe to execute under the kernel's verifier rules.

\subsection{Symbolic Policy Verification}

KRAKENGUARD provides a relevant baseline for fine-grained eBPF isolation. Its verification pipeline lifts eBPF bytecode into an intermediate representation, resolves helpers and other symbols, constructs a verification harness, and uses KLEE-based symbolic execution to explore policy-relevant behavior \citep{patel2026krakenguard}. This makes symbolic execution useful for cases where the policy decision depends on values that cannot be determined by simple local inspection.

The drawback is that symbolic execution can require exploration of multiple feasible execution paths. If a program has $P$ feasible paths, the symbolic workload can increase as $P$ increases. The exact relationship is workload dependent; this paper does not assume a universal asymptotic complexity. Instead, E2 experimentally controls path growth in a synthetic family.

\subsection{Why a Hybrid Approach?}

A verifier that sends every program directly to symbolic execution pays the complete symbolic pipeline cost even when the policy decision is already obvious from the program's compiled structure. A conservative abstract analyzer can sometimes prove that a forbidden action is unreachable or that all reachable policy-relevant operations are compliant.

The key design principle is therefore:
\begin{equation}
H(P,\Pi)=
\begin{cases}
\mathrm{ACCEPT}, & A(P,\Pi)=\mathrm{SAFE},\\
\mathrm{REJECT}, & A(P,\Pi)=\mathrm{VIOLATION},\\
V_{\mathrm{sym}}(P,\Pi), & A(P,\Pi)=\mathrm{UNKNOWN}.
\end{cases}
\end{equation}
Here, $A$ is the abstract analyzer and $V_{\mathrm{sym}}$ is the authoritative symbolic verifier. The hybrid method does not claim that symbolic execution becomes intrinsically faster. Its potential benefit comes from avoiding symbolic execution entirely for programs that the abstract stage can decide.

\subsection{Research Objectives and Questions}

The research problem is to reduce unnecessary symbolic policy-verification work without converting uncertainty into an unsafe decision.

The primary research question is:
\begin{quote}
Can inexpensive abstract policy analysis discharge policy-safe eBPF programs before symbolic execution, while selectively forwarding unresolved programs to symbolic verification?
\end{quote}

The evaluation is divided into two logical questions. First, can the abstract stage safely classify a useful subset of programs? Second, does avoiding symbolic verification reduce complete end-to-end verification cost?

The Phase 5 hypotheses are evaluation targets, not findings until the full execution matrix is available and independently checked:
\begin{itemize}
    \item \textbf{H5-C: Correctness.} Abstractly discharged final decisions agree with the frozen symbolic reference on the validation corpus.
    \item \textbf{H5-COV: Selective discharge.} A measurable subset of the corpus can be classified without symbolic fallback.
    \item \textbf{H5-P: End-to-end cost.} Hybrid verification reduces complete verification time when abstract-analysis cost plus any required fallback cost is lower than symbolic-only verification.
    \item \textbf{H5-S: Fallback scaling.} Fallback amount and cost can be characterized as symbolic path complexity increases.
\end{itemize}


\section{Review of Literature}

Recent eBPF research covers several dimensions of the security and isolation problem. KRAKENGUARD directly addresses fine-grained eBPF isolation using symbolic analysis and serves as the primary baseline for this study \citep{patel2026krakenguard}. BCF applies proof-guided abstraction refinement to improve verifier precision while constraining kernel complexity \citep{sun2025bcf}. Approximation Enforced Execution investigates runtime enforcement for untrusted Linux kernel extensions and changes the assumptions around verifier enforcement \citep{sun2025aee}. Veritas/SpecCheck uses specification-based testing to detect eBPF verifier misbehavior \citep{lyu2025veritas}.

Multi-tenant execution isolation is also being investigated independently of policy verification. vBPF explores eBPF virtualization and tenant/state isolation \citep{zhang2026vbpf}, while PeeR addresses scheduling and resource isolation for latency-critical eBPF applications \citep{carin2026peer}. BPF Token changes the delegation model for BPF operations through user-namespace-bound BPF filesystems \citep{bpftoken}. SeaBee addresses protection of security-critical eBPF infrastructure against privileged tampering \citep{seabee}.

These systems motivate the broader multi-tenant security context but do not make them interchangeable baselines for the specific policy-verification experiment in this paper. In particular, the present work evaluates a hybrid verification strategy against a frozen KRAKENGUARD policy-analysis configuration rather than proposing a new BPF namespace, virtualization layer, scheduler, or verifier.

The analyzer operates on the compiled eBPF object and its control-flow graph rather than relying only on source-level C syntax. This distinction follows from the semantics of the BPF instruction set and the Linux toolchain, in which source constructs may be optimized or transformed before verification \citep{linuxbpfdocs,thaler2024bpfisa}. It tracks reachability, selected integer facts, policy conditions, helper access, map access, memory ranges, return values, and analysis status.

\subsection{Three-Valued Abstract Decision}

The analyzer returns exactly one of three abstract decisions:
\begin{itemize}
    \item \textsc{Safe}: every reachable abstract state is proven policy compliant.
    \item \textsc{Violation}: a policy-forbidden action is proven reachable.
    \item \textsc{Unknown}: the available abstract domain cannot prove compliance or violation.
\end{itemize}

The distinction between \textsc{Unknown} and \textsc{Safe} is fundamental. Unsupported instructions, unknown helper identities, unresolved map identity or access mode, insufficient memory proofs, and unresolved branch conditions conservatively produce \textsc{Unknown}. A syntactic occurrence of a forbidden operation is not sufficient for \textsc{Violation} unless its reachability is established.

\subsection{Fail-Closed Semantics}

The analyzer is designed around a one-sided safety requirement: an abstract analysis failure must reduce precision, not increase authority. Therefore:
\[
    \mathrm{UNKNOWN} \not\Rightarrow \mathrm{SAFE}.
\]
Only the symbolic fallback can resolve an unresolved case. This design also makes the hybrid system compatible with the role of KRAKENGUARD as the authoritative reference for the experiments.

\section{Research Methodology}

\subsection{Frozen Baseline and Environment}

All experiments use a frozen KRAKENGUARD revision:
\[
\texttt{e7bd84005b304c5a10efcdb04914d1882b3cccf7}.
\]
The fixed policy used by E1 and Phase 5 has SHA-256:
\[
\texttt{270403272d736ae7aee2ceda3bf8d088b6ac0cb476bb99ce0218dd8f33c3c603}.
\]

The experimental environment is:
\begin{itemize}
    \item Linux kernel 7.2.3-arch1-2, x86\_64;
    \item AMD Ryzen 5 5600H, 12 logical cores;
    \item approximately 7.1 GiB RAM;
    \item Clang/LLVM 22.1.8;
    \item BPF target with \texttt{-mcpu=v1};
    \item optimization \texttt{-O2 -g};
    \item XDP hook type;
    \item Docker-based KRAKENGUARD artifact with immutable image digest \texttt{sha256:9633a6922518589803a4c9b8123d0549e54b5f57c1d04f9e383e822fd9ae3bd4}.
\end{itemize}

The compiler flags were \texttt{-target bpf -mcpu=v1 -D\_\_TARGET\_ARCH\_x86 -O2 -g} with the required system include path.

\subsection{Phase 5 Corpus}

The Phase 5 validation corpus contains 24 programs divided equally into four categories:
\begin{itemize}
    \item \textbf{A:} abstractly provable compliant, 6 programs;
    \item \textbf{B:} abstractly uncertain but symbolically compliant, 6 programs;
    \item \textbf{C:} abstractly provable violation, 6 programs;
    \item \textbf{D:} abstractly uncertain and symbolically violating, 6 programs.
\end{itemize}

This structure separates easy cases from cases that intentionally require the symbolic fallback.

\subsection{E3: Selective Discharge and Correctness}

E3 is specified to evaluate whether the abstract stage can classify a useful subset and whether discharged decisions agree with the frozen symbolic reference. The protocol calls for two warmups and seven measured repetitions for each of 24 programs, producing 216 planned executions.

The primary endpoint is:
\[
D=\frac{N_{\mathrm{SAFE}}+N_{\mathrm{VIOLATION}}}{N_{\mathrm{total}}}.
\]

A correct hybrid decision is defined relative to the authoritative KRAKENGUARD result. The experiment requires zero false SAFE and zero false VIOLATION decisions; false UNKNOWN is acceptable because it invokes the fallback.

\subsection{E4: End-to-End Performance}

E4 compares two complete pipelines:
\begin{align}
T_{\mathrm{symbolic}} &= T_{\mathrm{KRAKENGUARD}},\\
T_{\mathrm{hybrid}} &=
\begin{cases}
T_{\mathrm{abstract}}, & \text{if discharged},\\
T_{\mathrm{abstract}}+T_{\mathrm{fallback}}, & \text{otherwise}.
\end{cases}
\end{align}

The E4 protocol specifies both conditions for each of 24 programs, with two warmups and seven measured repetitions per condition, for $24\times2\times9=432$ planned executions. This protocol total must not be confused with verified evidence that all runs completed. Conditions were interleaved using deterministic randomization with seed 42. The primary endpoint is paired per-program median end-to-end wall time.

\subsection{E5: Fallback Scaling}

E5 is designed to examine hybrid behavior across symbolic path strata. The corpus design identifies 1, 2, 4, 8, 16, and 32 as reachable strata; 64 was marked unreachable for eligible Phase 5 programs. These are design/summary claims and require the underlying execution artifacts before being treated as independently verified observations.

The experiment reports abstract time, fallback time, total hybrid time, and fallback fraction. It does not assume that the abstract analyzer accelerates symbolic execution itself. Its intended benefit is elimination of unnecessary symbolic invocations.

\section{Results / Findings}

\subsection{E1: Program Features Do Not Explain Cost on Their Own}

The E1 dataset contains eight programs, each with two warmup and seven measured executions. The independent evidence audit found 72 rows, unique run identifiers, consistent policy and baseline identifiers, and exact agreement between the recorded CSV measurements and JSON aggregates. It therefore passed the dataset-integrity check, with qualifications about the meaning of several instrumentation fields.

The median wall times in Table~\ref{tab:e1} lie in a narrow range despite the increase in compiled instruction count. This is evidence only about the tested micro-corpus and pipeline. It does not establish that program size is irrelevant in general. The audit also found that one source-level branch had been optimized away by Clang, that the reported basic-block count was heuristic, and that the field named \texttt{verifier\_states} represented KLEE's explored-path statistic. Those qualifications limit how strongly the table can be interpreted.

\subsection{E2: Controlled Path Growth}

The E2 project record reports a controlled family with 1, 2, 4, 8, 16, 32, and 64 feasible symbolic paths. The median increased from 746.14~ms at one path to 1231.16~ms at 64 paths, an increase of approximately 65\%. A linear fit of roughly
\[
T(P)\approx 740+7.6P\ \mathrm{ms}
\]
summarizes the tested range. It is a descriptive fit, not a complexity theorem. The observation motivates testing whether a selective front-end can reduce the number of programs that require symbolic execution.

\subsection{Phase 5: Prototype and Evaluation Status}

The repository contains the three-valued abstract analyzer, a 24-program policy-directed corpus, correction and fallback validation records, a frozen execution specification, and the E3--E5 experimental protocol. The protocol defines three questions: how many cases can be discharged without symbolic execution (E3), whether hybrid execution reduces complete end-to-end cost (E4), and how fallback behaves across reachable path strata (E5).

However, the final independent results audit did not accept E3--E5 as completed experiments in the audited repository state. It found that the claimed execution commit and the required raw result sets were unavailable for independent recomputation. The summaries below are therefore evidence about the project's intended evaluation design, not accepted experimental outcomes.

\section{Discussion}

The project provides a useful example of why systems-security papers need to separate a plausible optimization from a demonstrated one. E1's audited measurements show that, for this small compiled micro-corpus, instruction count alone does not account for the end-to-end verification time. The audit's compiler and instrumentation qualifications are equally important: the branch structure in the object differed from source-level intent, and some counters were proxies rather than direct measurements.

E2 addresses a different dimension by varying the feasible symbolic path count in a controlled program family. Its recorded timing trend supports the motivation for selective analysis within the tested range. It does not show that every real-world workload will follow the same relationship, nor does it by itself demonstrate that a hybrid design will be faster. That second claim depends on the fraction of cases discharged, the cost of abstract analysis, and the cost of fallback.

The abstract analyzer is designed around this distinction. It returns \safe, \violation, or \unknown; it does not treat uncertainty as permission. The three-valued interface gives the system a way to preserve the symbolic verifier as the authority for cases that the abstract domain cannot settle. This is the central design rationale and is independent of whether the current Phase 5 performance hypothesis is ultimately confirmed.

The project's reported Phase 5 summaries would, if verified, suggest a trade-off that is worth testing: conclusively discharged cases could avoid symbolic execution, while fallback cases would pay the abstract-stage overhead before receiving the reference verdict. But the raw E3/E4/E5 artifacts were not available to the final independent results audit. The 50\% discharge and 45.53\% savings values are therefore not used as evidence for this paper's conclusions. They should be treated as testable claims pending artifact recovery or a new execution campaign.

The engineering record also includes an unsuccessful attempt to run a real-world Katran object through the frozen verifier. Because the attempt did not produce an authoritative policy result, it cannot support a performance comparison. It instead points to a practical requirement for future work: establish compatibility and obtain a valid baseline verdict before interpreting timing data from a production-oriented program.

\section{Limitations of the Study}

Several limitations bound the conclusions.

\subsection{Corpus Scope}
The Phase 5 corpus contains 24 synthetic, policy-directed XDP programs. It is useful for controlled evaluation of the decision categories but is not representative of all production eBPF workloads. Large programs, complex parsers, large maps, tail calls, loops, and application-specific policies may exhibit different behavior.

\subsection{Reference Oracle}
Correctness is measured against the frozen KRAKENGUARD configuration. Agreement with a reference implementation establishes consistency with that implementation; it does not independently prove universal correctness of KRAKENGUARD.

\subsection{Environment}
All measurements were collected on one host, one kernel version, one compiler version, one XDP configuration, one frozen KRAKENGUARD revision, and one fixed policy. Results may differ on other systems.

\subsection{Path Range}
E2 experimentally covers 1--64 feasible paths. E5 reaches only 1--32 paths for eligible Phase 5 programs; the 64-path Phase 5 stratum was unreachable. No claim is made about behavior beyond these ranges.

\subsection{Measurement Scope}
Wall time is measured for the complete verification workflow. Client-process CPU time is not treated as equivalent to verifier wall time. Memory scaling and detailed solver-time scaling are not used as primary conclusions because they were not consistently exposed by the frozen pipeline.

\subsection{Generalization}
The previously reported 50.0\% discharge rate and 45.53\% savings figure could not be independently recomputed because the required raw E3--E5 result sets were absent from the final audit. They are not established findings and must not be interpreted as measured performance outcomes until the raw artifacts are recovered or the experiments are rerun.

\section{Reproducibility and Provenance}

The repository specifies the major controls needed to reproduce the configuration: KRAKENGUARD revision, policy hash, compiler, kernel, architecture, hook type, compiler flags, container image digest, corpus metadata, and expected raw execution artifacts. For Phase 5, however, the final independent results audit did not find the complete execution artifacts needed to recompute the reported results.

The repository records Phase 5 design, correction-validation, fallback-validation, and execution-gate artifacts. The gate review authorized execution; it did not establish that the performance experiments had run. The independent results audit explicitly found that the claimed execution commit and E3/E4/E5 raw result sets were absent from the audited repository state. Consequently, the E3 discharge counts, E4 timing summaries, and E5 scaling table elsewhere in older result summaries are not treated here as completed, independently reproducible experiments. A provenance record or README summary is not a substitute for raw execution rows and a reproducible aggregation path.

This evidence boundary is consequential: the manuscript reports E1 as an audited baseline with qualifications, treats E2 as a controlled baseline result from the project records, and describes E3--E5 as an implemented design and planned evaluation whose claimed outcome numbers require artifact recovery and independent recomputation before publication.

\section{Recommendations / Implications}
The immediate recommendation is to recover the immutable Phase 5 execution tree or rerun E3--E5, preserve all raw rows, and independently regenerate every summary from a versioned analysis script. The report should include per-program paired timings, abstract-stage overhead, fallback time, discharge coverage, mismatch counts, failures, timeouts, and uncertainty summaries. Any correctness mismatch must block a performance claim until its cause is understood.

For deployment, keep the abstract analyzer conservative, pin the policy and verifier versions, and treat unsupported semantics, timeouts, crashes, and malformed outputs as non-accepting outcomes. Evaluate additional program types, hooks, helper sets, map behaviors, and kernels before claiming broad applicability. Operational isolation of the analysis process and resource limits remain necessary; this analyzer is not a replacement for the Linux kernel verifier or a complete tenant-isolation mechanism.

\section{Conclusion}

This project began with a broad interest in multi-tenant eBPF confinement and narrowed the thesis question after reviewing newer work on fine-grained isolation, verifier precision, delegation, virtualization, and scheduling. That review matters: a new namespace, a generic LSM policy, or another verifier-testing tool would overlap with existing systems and would not by itself establish a defensible contribution. The surviving question is more specific: can a conservative abstract front-end avoid some symbolic policy-verification work without changing the final security decision?

The strongest completed empirical evidence currently available is the baseline characterization. E1 passed an independent data-integrity audit with qualifications, including compiler transformations that changed the intended branch structure and instrumentation fields that must not be over-interpreted. E2's controlled family showed increasing end-to-end cost from one to 64 feasible paths. Those observations motivate selective analysis, but they do not alone demonstrate that the hybrid system improves end-to-end performance.

The project also produced an abstract analyzer, a structured 24-program corpus, fail-closed handling for unsupported or unresolved semantics, a frozen policy and environment specification, and an execution protocol for E3--E5. The currently audited repository does not, however, contain the raw Phase 5 execution artifacts needed to independently substantiate the frequently reported 50\% discharge rate and 45.53\% timing savings. Those numbers are therefore excluded from the paper's established findings. Recovering the immutable execution tree, checking every run, and regenerating the aggregates is the immediate prerequisite to making a performance claim.

This distinction does not make the project less useful; it makes the paper more defensible. The contribution at this stage is a carefully bounded hybrid design, a baseline analysis, and a reproducible evaluation plan with explicit failure semantics. Future work should complete the Phase 5 evidence audit, expand the corpus beyond synthetic XDP programs, measure additional hooks and policy forms, and investigate targeted refinement for cases that return \unknown. A separate real-world Katran attempt also exposed a compatibility boundary: the attempted run terminated before producing a valid verification result, so it is an engineering lesson rather than evidence of successful production-workload evaluation.
